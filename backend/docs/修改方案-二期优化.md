## 1. P0 安全加固（上线前必做）

### 1.1 现状盘点

- `configs/config.yaml` 里明文放了 `mysql.password: "123456"`、`jwt.secret: "随便填一个长字符串"`，会随仓库一起提交。
- `config.go:62-64` 已 `BindEnv` 了 `mysql.password`、`jwt.secret`、`app.mode`，但 **Redis 密码没有 BindEnv**。
- `redis.go:21` 其实已经用了 `cfg.Redis.Password`（`redis.Options.Password`），客户端层是通的，只差环境变量注入这一步。
- `config.yaml:4` 默认 `mode: debug`，`router.go` 未按 release 模式 `gin.SetMode`，也没有「release 下必须强 secret」的校验。

### 1.2 改动清单

1. **移除 yaml 里的明文敏感项**
   - `jwt.secret` 改为空占位（例如 `secret: ""`），实际值走 `JWT_SECRET` 环境变量。
   - `mysql.password` 同理，走 `MYSQL_PASSWORD`。
   - `redis.password` 走 `REDIS_PASSWORD`（新增绑定）。

2. **`config.go` 补充环境变量绑定**（在 `LoadConfig` 内、`ReadInConfig` 之前）：
   ```go
   viper.BindEnv("mysql.password", "MYSQL_PASSWORD")
   viper.BindEnv("jwt.secret", "JWT_SECRET")
   viper.BindEnv("redis.password", "REDIS_PASSWORD") // 新增
   viper.BindEnv("app.mode", "APP_MODE")
   ```

3. **release 模式强制校验**（`LoadConfig` 末尾，`Unmarshal` 之后加一个 `validateProductionConfig()`）：
   - 当 `config.App.Mode == "release"` 时：
     - `jwt.secret` 长度必须 ≥ 32，且不等于占位串 `"随便填一个长字符串"`，否则 `panic` 拒绝启动；
     - `mysql.password` / `redis.password` 为空也拒绝启动（Redis 密码可放宽，视部署而定）。
   - 同步在 `router.NewEngine()` 里按 mode 设置 `gin.SetMode(gin.ReleaseMode)`（或在 `main.go` 里设置，二选一，推荐 main.go）。

4. **生成强随机 secret 的运维命令**（PowerShell）：
   ```powershell
   [Convert]::ToBase64String((1..48 | ForEach-Object { Get-Random -Minimum 0 -Maximum 256 }) -as [byte[]])
   ```
   或 `openssl rand -base64 48`。

5. **`.gitignore` / `.env.example`**
   - 新增 `.env.example`，列出 `JWT_SECRET`、`MYSQL_PASSWORD`、`REDIS_PASSWORD`、`APP_MODE` 示例。
   - 确认 `configs/config.yaml`（若保留本地值）与 `.env` 不进版本库；生产用 `APP_ENV=production` 加载 `config.production.yaml`（`config.go:55-57` 已支持按 `APP_ENV` 选配置文件）。

### 1.3 验收

- `APP_MODE=release` 且不注入 `JWT_SECRET` 时，启动应直接 panic 退出（不静默降级）。
- 注入环境变量后可正常启动，`/health` 返回 `ok`。

## 2. P1 会员数据

### 2.1 现状

- `model/user.go:13-15` 三个字段 `RealName` / `ClassName` / `Department` 均为 `string`，GORM 建的列默认可空。
- 老用户（id=1~5）这三列为 `NULL`；新注册用户由注册接口写空串或实际值。
- `admin_user_service.List` 已有 `department` 精确筛选、`keyword` 已含 `real_name` 搜索；排序已把「空 real_name」排到最后。
- `GET /profile`（`member_service.go:23`）返回完整 `User`，已含 `real_name` / `class_name` / `department`，前端可本地判断是否完善。

### 2.2 改动清单

**A. NULL → 空串一次性迁移**

先跑 SQL（务必在改 model tag 之前）：

```sql
UPDATE users
SET real_name   = COALESCE(real_name, ''),
    class_name  = COALESCE(class_name, ''),
    department  = COALESCE(department, '');
```

可选加固：把三个字段的 GORM tag 加上 `default:'';not null`（`model/user.go`），这样以后不可能再出现 NULL。**顺序必须是先迁移数据、再改 tag 并重启**，否则 AutoMigrate 加 `NOT NULL` 会因存在 NULL 行而失败。

**B. 登录后补资料引导**

- 后端无需新接口：`GET /profile` 已返回三字段。
- 前端 `MemberPortal`（会员中心）在拿到 profile 后本地判断：`real_name` / `class_name` / `department` 任一项为空，则在页面顶部渲染引导横幅（「你的会员资料不完整，请补充姓名/班级/部门」+ 跳编辑入口按钮）。
- 判断逻辑建议抽成 `profileIsComplete(user)` 工具函数，供登录后其它视图复用。

**C. 后台「未完善会员」筛选**

- `admin_user_handler.List`（`admin_user_handler.go:20`）新增读取 `incomplete` query（`0`/`1`）。
- `admin_user_service.List` 增加入参 `incomplete bool`，当为 true 时追加：
  ```go
  tx = tx.Where("(real_name = '' OR class_name = '' OR department = '')")
  ```
- 前端 `AdminView` 用户列表加一个「未完善会员」筛选开关/按钮，调用 `adminListUsers({ incomplete: '1' })`。

### 2.3 验收

- 迁移后 `SELECT real_name, class_name, department FROM users WHERE id IN (1,2,3,4,5)` 全部为 `''` 而非 `NULL`。
- 后台「未完善会员」能筛出三字段任一为空的人。

## 3. 聊天室 WebSocket（重中之重）

### 3.1 为什么非改不可

当前 `ChatView.tsx:194-228` 是 2 秒轮询 `GET /chat/messages`（`document.hidden` 降频到 10 秒）。并发上去后，每 2 秒全员打一次接口，且 `ListMessages` 每次都要 `touchPresence` + 查 Redis，QPS 与 Redis 压力随在线人数线性上涨。改 WS 后只有「消息/上下线/撤回」事件才推一次，服务端和 Redis 压力从「定时全量」变成「事件驱动」，这是扛并发最有效的一刀。

### 3.2 依赖

- `go.mod` 无 websocket 库，需引入 `github.com/gorilla/websocket`（`go get github.com/gorilla/websocket`）。

### 3.3 端点与握手鉴权

- 新增路由：`GET /api/v1/chat/ws`（挂到 `registerAuthRoutes` 的 `auth` group 之外，因为 WS 握手走自己的鉴权，不进普通 JWT 中间件）。
- **鉴权难点**：浏览器 `new WebSocket()` 无法自定义 `Authorization` header。
  - **推荐方案（子协议）**：前端 `new WebSocket(url, ['bearer', token])`，把 token 塞进 `Sec-WebSocket-Protocol`。服务端 `Upgrader` 前读 `r.Header.Get("Sec-WebSocket-Protocol")`，拆出 `bearer` 与 token 后校验。token 不进 URL、不进 access log。
  - 备选（query）：`/chat/ws?token=...`，实现最省，但 token 会进日志，作为降级即可。
- **复用现有校验逻辑**：把 `middleware/jwt.go` 里「Redis `token:<t>` 存在 + `utils.ParseToken`」这段抽成一个纯函数（例如 `AuthenticateToken(rdb, token, prefix) (claims, error)`），HTTP 中间件与 WS 握手共用，避免两套实现漂移。

### 3.4 消息信封（统一 JSON）

服务端 → 客户端统一格式：

```json
{ "type": "message" | "presence" | "delete" | "pong", "data": { ... } }
```

| type | data 内容 | 触发时机 |
| --- | --- | --- |
| `message` | 单条 `ChatMessage`（含 `real_name`/`department`，复用 `fillUserInfo`） | 有人发文本/文件/系统消息 |
| `presence` | `{ "online_count": n }` | 有人上下线 |
| `delete` | `{ "ids": [123, 456] }` | 有人撤回 / 管理员删除 |
| `pong` | `{ "ts": 1234567890 }` | 回应客户端心跳 `ping` |

客户端 → 服务端：`{ "type": "ping", "data": { "ts": ... } }`（心跳），以及可选的 `{ "type": "message", "data": { "content": "..." } }`（若文本也走 WS 发送）。

### 3.5 服务端 Hub 设计

- 新增 `internal/ws/`（或并入 chat 相关文件），实现内存 Hub：
  - `Hub{ clients map[uint][]*Client; register/unregister/broadcast chan ... }`
  - `Client{ conn *websocket.Conn; userID uint; send chan []byte }`
  - 每个连接一个读 goroutine + 一个写 goroutine，写侧带 `send` 缓冲，防慢客户端阻塞广播。
- **连接建立 = 加入聊天室**：握手成功后调用现有 `ChatService.Join(userID)`（复用落库 + presence + 系统消息「xxx加入聊天室」），断连/超时调用 `Leave(userID)`。
- **发送路径**：`SendText` / `SendFile` 落库成功 → `hub.Broadcast(messageEnvelope)`；撤回/管理员删除 → `hub.Broadcast(deleteEnvelope)`。
- **历史消息仍走 HTTP**：`GET /chat/messages`（`ListMessages`）保留，只负责初次加载与「查看更早消息」，WS 只推实时增量。这样断线重连后，前端先 HTTP 拉增量补齐，再继续 WS，避免漏消息。
- **心跳**：服务端给每个连接设 `ReadDeadline`（如 60s）+ `PongHandler` 续期；客户端每 30s 发 `ping`。

### 3.6 多实例 Redis Pub/Sub（预留，非本期必须）

- 单机部署：内存 Hub 足够。
- 若未来多实例（水平扩展），`SendText/SendFile` 落库后 `PUBLISH chat:broadcast <envelope>`，每个实例启动时 `SUBSCRIBE chat:broadcast`，收到后推给本实例的本地客户端。现有 Redis 已承载 `chat:stream`/`chat:presence`，加一个 Pub/Sub channel 成本极低。本期先留出 `broadcast()` 接口，实现内存版，Pub/Sub 作为后续开关。

### 3.7 前端改造

- 新增 `frontend/src/lib/ws.ts`：
  - `connectChatWS(onMessage, onClose)`：用子协议鉴权建连；指数退避自动重连（如 1s/2s/4s…上限 30s）；30s 心跳；断线回调。
  - `sendChatWS(payload)`：封装发送。
- `ChatView.tsx` 改造：
  - 删除 `useEffect` 里的轮询（`ChatView.tsx:194-228`）。
  - `joined` 后建立 WS，按信封类型更新 state：`message` → `mergeMessages([msg])`；`delete` → `applyDeletedMessages(ids)`；`presence` → `setOnlineCount`。
  - `sendText` 改为 WS 发送文本（更快、更省），文件仍走 HTTP `sendChatFile`（multipart 不适合走 WS）。
  - 保留 `loadHistory` / `loadEarlier` 的 HTTP 逻辑不变；WS 断线重连后先 `getChatMessages({ afterId })` 补齐缺口再继续。

### 3.8 验收

- 两个浏览器会话同时在线，A 发消息，B 无刷新即时收到（不再等 2 秒）。
- 断网 5 秒再恢复，WS 自动重连且不丢消息。
- 上线/下线时，其余在线用户即时看到 `online_count` 变化。
- `go build` + `go vet` + 前端 `tsc --noEmit` 全绿。

## 4. 会员批量操作

### 4.1 改动清单

- **Service 层**（`admin_user_service.go`）新增三个方法，均用 `gorm` 事务 + `IN` 条件：
  - `BatchSetStatus(ids []uint, status int) error`
  - `BatchResetPassword(ids []uint, newPassword string) error`（复用单条的 bcrypt + 校验，密码只生成一次 hash，批量应用）
  - `BatchDelete(ids []uint) error`（软删除）
  - 额外：`BatchSetStatus` 建议排除当前管理员自身，避免误操作锁死后台。
- **Handler 层**（`admin_user_handler.go`）新增：
  - `POST /api/v1/admin/users/batch-status` → `{ ids, status }`
  - `POST /api/v1/admin/users/batch-reset-password` → `{ ids, new_password }`
  - `POST /api/v1/admin/users/batch-delete` → `{ ids }`
  - 路由加在 `router.go:282-286` 附近。
- **前端**（`AdminView`）：
  - 用户表格加复选框列 + 全选；顶部出现「批量禁用/启用」「批量重置密码」「批量删除」按钮。
  - 批量删除需二次确认弹窗（防止误删）。

### 4.2 验收

- 勾选 N 个用户批量禁用后，刷新列表状态全部为禁用，且被禁用户无法登录。
- 批量重置密码后，用新密码可登录。

## 7. 风险与注意事项

1. **WS 鉴权 token 生命周期**：现有 JWT 24h 过期 + Redis `token:<t>` 存续。WS 长连接若超过 token 有效期不会主动断（握手时校验一次）。建议 WS 心跳带 token 定期复验，或接受「握手时校验一次」的简化方案（内部社团站可接受）。落点：握手鉴权函数内做一次即可，文档默认取简化方案。
2. **常驻进程启动方式**：后端务必用 `Start-Process` 独立进程运行 `server.exe`，**禁止用后台任务跑**（600s 超时会被杀，历史上已踩过，聊天室会「进不去」）。
3. **迁移顺序**：先备份 → 跑 NULL 刷空串 SQL → 再改 model tag → 重启，顺序不可反。
4. **批量删除/禁用不可逆**：前端二次确认；`BatchSetStatus` 排除当前管理员。
5. **依赖新增**：`gorilla/websocket` 需要联网 `go get`，确认本机 go module proxy 可用；若离线，可改用标准库 `golang.org/x/net/websocket` 或手写 WebSocket 升级，但推荐 gorilla（最成熟）。
