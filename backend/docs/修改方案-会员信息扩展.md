# 会员信息扩展 — 修改方案报告（第二版）

> 目标：在注册、个人资料、聊天室、后台管理中新增「姓名 / 班级 / 部门（组织部、办公室、宣传部、外联部）」三项会员信息，并支持后台按部门筛选与 Excel 导出（仅姓名/班级/部门三列）。
>
> 本报告只做方案梳理，不含代码落地。所有文件路径、字段名、接口均已与 `math-top` 真实代码核对。

---

## 〇、本版决策定稿（相对第一版的变化）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 姓名、班级是否必填 | **必填**（注册时强制，资料更新时也不允许清空） |
| 2 | 「意向部门」怎么处理 | **改叫「注册部门」**，复用同一个 `department` 字段，不拆两个字段 |
| 3 | 老用户空值兜底 | 姓名/班级空 → 显示「未填写」；部门空 → 显示「未分配」。**只做展示层兜底，不写库、不加数据库默认值** |
| 4 | Excel 导出列 | **只导出三列：姓名、班级、部门**（担心数据泄露，最小化导出，不含昵称/用户名/邮箱/手机号等） |
| 5 | 部门是否必选 | 见第五节遗漏点 #6（建议一并必选，理由在下面） |

## 一、字段与可见性（定稿）

### 1.1 新增字段（加到 `users` 表）

| 字段 | Go 字段名 | 类型 | json tag | 含义 |
|---|---|---|---|---|
| 姓名 | `RealName` | `varchar(50)` | `real_name` | 真实姓名，必填 |
| 班级 | `ClassName` | `varchar(50)` | `class_name` | 所在班级，必填 |
| 部门 | `Department` | `varchar(20)` | `department` | 四选一：组织部/办公室/宣传部/外联部 |

> `Department` 加 `index`，后台要按它筛选。

### 1.2 部门枚举

写在 `internal/consts/consts.go`：

```go
var Departments = []string{"组织部", "办公室", "宣传部", "外联部"}
```

### 1.3 可见性边界（关键）

「内部统计需要（不公开）」这句话，落地要精确——**姓名和部门其实在「会员之间」的聊天室可见，只有班级是真正不公开**。建议把提示文案改准确（见第五节遗漏点 #8）。

| 字段 | 注册 | 本人资料 | 聊天室个人卡片 | 后台列表/导出 | 公开接口（活动/资讯/资源/作品/评论） |
|---|---|---|---|---|---|
| 姓名 `real_name` | 填写 | ✅ 可看可改 | ✅ 显示 | ✅ 显示/导出 | ❌ 不返回 |
| 班级 `class_name` | 填写 | ✅ 可看可改 | ❌ 不显示 | ✅ 显示/导出 | ❌ 不返回 |
| 部门 `department` | 选择 | ✅ 可看可改 | ✅ 显示 | ✅ 显示/筛选/导出 | ❌ 不返回 |

核心结论：三项都不进公开内容接口；姓名+部门在登录会员之间的聊天室可见；班级仅本人和后台可见。

## 二、数据库改动

`router.go` 里已经对 `model.User{}` 做了 `AutoMigrate`（`router.go:41-55`）。GORM 增量迁移会在模型加字段后自动给 `users` 表补列，**无需手写 SQL，也无需改迁移逻辑**。

**老用户**：三个新列会是空值。兜底统一在展示层做（后台列表、导出、聊天卡片、资料页），不写默认值、不改历史数据。

## 五、遗漏点清单（本次重点排查结果）

这些是第一版没覆盖、或容易踩坑的点，逐条给了处理方式。

**#1 登录/注册返回的 `user` 没带新字段**
`handler/user.go` 的 Login/Register 返回的 `gin.H` 目前只有 id/username/nickname/email/role/avatar（`user.go:49-57`、`user.go:71-81`）。前端 `loginUser` 会用这个返回直接 `setUser`（`auth.tsx:71-75`），若不带新字段，登录后首屏资料页/聊天卡片会缺姓名部门，得等 `refreshUser` 再拉一次。**建议 Login/Register 返回里补上 `real_name`/`class_name`/`department`**。

**#2 种子数据要补字段**
见 3.9。

**#3 资料更新时姓名/班级的必填校验**
`UpdateProfile` 目前用 `Updates(map)` 白名单更新。加字段后，若前端传空字符串会把必填项清空。**服务端要在 `member_service.go` 里对姓名/班级做非空校验**，传空直接报错。

**#4 后台 `keyword` 搜索要不要加姓名**
现在搜的是 username/nickname/email（`admin_user_service.go:32`）。既然后台以姓名为首，建议加上 `real_name LIKE`。已纳入 3.6。

**#5 列表顺序 vs 导出顺序不一致**
你第一次说列表「姓名→部门→班级」，最新说导出「姓名→班级→部门」。两处顺序不同。**建议统一为「姓名→部门→班级」**（跟列表一致，导出仍只保留这三列）。下面按此建议写，若你要严格按「导出=姓名→班级→部门」执行，导出那处单独调一下即可。

**#6 部门是否必填**
你只明确了「姓名、班级必填」，部门没明说。但「注册部门」语义 + 后台要按部门筛选，部门留空会堆出一堆「未分配」、筛选也筛不全。**建议部门也设为必选**（注册下拉无默认值、前端校验必选）。若你想部门可选，我再把校验放开。

**#7 前端部门下拉的数据源**
建议前端**硬编码** `["组织部","办公室","宣传部","外联部"]`（注册、资料、后台筛选三处复用同一常量），后端 `consts.Departments` 做最终校验兜底。不必为此新增「获取部门枚举」接口，避免前后端两处枚举漂移。

**#8 「不公开」提示文案不准确**
姓名和部门其实会在聊天室会员间显示，真正不公开的只有班级。注册页那句「内部统计需要（不公开）」容易误导用户以为姓名也完全保密。建议改成类似「内部统计与会员名片展示使用（仅登录会员可见）」，班级单独标「仅后台可见」。

**#9 `repository` 层 `List` 其实没接线**
`internal/repository/user_repository.go` 定义了 `List` 和 `UserFilter`，但后台列表实际走的是 `admin_user_service.List`（直接 `s.db`），`UserRepository` 没被主要 service 使用。**本次不需要同步改 repository 层**，避免白改；若你计划后续把 repository 接上，再一并处理。

**#10 导出文件名中文编码**
`Content-Disposition` 直接塞中文文件名在某些浏览器会乱码。建议用 RFC 5987：`filename="members.xlsx"; filename*=UTF-8''%E4%BC%9A%E5%91%98%E5%90%8D%E5%8D%95.xlsx`，或干脆用英文名（如 `members-组织部.xlsx` 里的中文部门名也建议编码）。

**#11 导出是文件流，前端不能复用 `request`**
`http.ts` 的 `request` 最后固定 `res.json()`，遇到二进制会抛「请求失败」。导出需要单独一个走 `res.blob()` + `URL.createObjectURL` 下载的函数，且要带 admin token。

**#12 聊天室卡片的实时性**
`cacheMessage` 缓存的是不含 `fillUserInfo` 的原始消息，`fillUserInfo` 每次拉消息实时查 DB 回填，所以改资料后新消息即生效，无需额外清缓存。放心。

**#13 空部门筛选（可选增强）**
后台筛选下拉除「全部 + 四个部门」外，可加一个「未分配」选项，方便定位没填部门的老用户。非必须，做了更顺手。

## 六、影响与风险

- **数据库**：`AutoMigrate` 自动加列，无破坏性；老用户三字段为空，靠展示层兜底，不写默认值。
- **隐私**：三项字段只出现在 `profile`（本人）、聊天消息 `fillUserInfo`（姓名+部门，会员间可见）、后台列表/导出（管理员）三处；公开内容接口不新增这些字段，不会外泄。
- **新依赖**：`excelize/v2` 纯 Go、跨平台稳定，会拉入少量子依赖。
- **导出接口**：必须挂在 admin 鉴权之后，仅管理员可导出会员名单。
